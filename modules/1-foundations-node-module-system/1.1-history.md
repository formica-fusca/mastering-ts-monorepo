## Why CommonJS exists

Node launched in 2009 into a language with **no module system**. Browser JS shared one global
scope, managed by `<script>` ordering and IIFEs.

Ryan Dahl did not invent CommonJS — he **adopted** it. CommonJS was a community spec effort
begun in January 2009 (originally *ServerJS*, by Kevin Dangoor) to define server-side JS APIs,
and Node implemented a variant of its module proposal. Worth keeping straight: the format Node
is permanently stuck with was designed by a mailing list, in parallel, for a slightly
different purpose.

The consequential decision: **`require()` is synchronous**. It blocks, reads the file,
executes it, returns the exports object. On a server with a local disk that is entirely
reasonable — it is just a function call.

## The trade: what "ergonomic" bought, and what it cost

Because `require` is an ordinary function call, CJS gets a long list of conveniences. Each one
is paid for with a static guarantee:

| CJS can do this… | …so you lose | Where it bites in this program |
|---|---|---|
| `require(\`./drivers/${env}\`)` — computed specifiers | the dependency graph is unknowable without **running** the code | bundlers must guess; `affected` graphs (5.1, 5.3) need statically readable imports |
| `if (x) require('./heavy')`, `require` inside a function | load order, and *what loads at all*, are runtime facts | no reliable dead-code elimination |
| exports are a **mutable runtime object** — built in a loop, reassigned, computed | no static export list exists | the named-import problem; why `cjs-module-lexer` had to be invented |
| `require('x').foo = stub` — patch another module's exports | modules can be mutated from outside | ESM namespaces are **sealed** (`isExtensible → false`); stubbing tricks die |
| `const { a } = require('x')` anywhere — in a branch, a loop, a function | imports need not be top-level | ESM restricts imports to top level; `import()` is the escape hatch |

Read the middle column top to bottom and you have the working definition of *static*: **the
shape of the program is knowable without executing it.** CJS surrenders that five separate
ways, each for a real convenience.

This matters far beyond trivia, because **monorepo tooling is almost entirely static
analysis**. "Which packages changed?", "what depends on this?", "what is cacheable?", "what
can be pruned into the Docker image?" — every one of those is answerable only if imports are
statically readable. Modules 5 and 8 cash the cheque ESM wrote.

## Why the browser could never run CommonJS

Synchrony also broke the browser: you cannot block on a network fetch for every `require`.
Hence AMD/RequireJS, and later Browserify and webpack. **Bundlers began life as a workaround
for CJS's synchrony**, not as a build optimisation. That origin still shows in Module 5.

## Interlude — what a browser page actually looked like

*(Student question: "back then, browser pages were all server-side rendered?")*

Half right, and the correction is instructive.

**Right:** in 2015 HTML overwhelmingly arrived from the server fully formed — Rails, Django,
PHP, JSP, ASP.NET. JavaScript was *progressive enhancement* on top of HTML that already
worked.

**Anachronistic:** calling that "server-side rendering". At the time it was simply web
development; there was no other kind, so it needed no name. **"SSR" is a retronym** — it
exists only because client-side rendering appeared and the old way needed distinguishing. And
today "SSR" means something narrower still: rendering a *component framework* on the server
and hydrating it in the browser, a 2016-ish idea.

The timeline is also not "server-rendered, then modules":

```
2009  Node. RequireJS.
2010  Backbone. AngularJS.
2011  Browserify — "run CJS in the browser"
2012  webpack
2013  React
2015  ES2015 modules standardised     <- the syntax finally exists
2016  Next.js
2017  Node ships --experimental-modules
```

SPAs predate ESM by years. But they were built with **bundlers** and delivered as one large
`<script>`. Server-rendered page or SPA, what the browser received was `<script src="...">` —
not modules.

**The connection that actually matters.** Because the server (or the build) assembled the
page, the server also decided *which scripts to include and in what order*. Dependency
resolution happened at authoring or build time, performed by a human writing tags or by a
template. **The browser never resolved anything, because somebody upstream already had.**

Bundlers are the automation of precisely that job — "the server decides the script list",
mechanised. Native ESM in 2015 was the first time anyone asked **the browser itself** to
resolve a dependency, and that is when everyone discovered it had no way to.

And it is still mostly not the browser's job: production apps overwhelmingly ship bundles.
Vite serves native ESM in *dev* and bundles for *prod*. So when you configure a bundler in a
monorepo you are operating the load-bearing workaround, not incidental tooling.

## Why ES2015 standardised no loader

*(Student question: "why did ES2015 deliberately specify no loader?")*

**1. TC39 specifies the language; hosts specify the environment.** ECMAScript deliberately
contains no I/O — no filesystem, no network, no `console`. Module *resolution* is I/O plus a
notion of where modules live, and those differ irreconcilably:

```
browser                     server
───────                     ──────
URLs                        filesystem paths
HTTP + CORS                 node_modules walking
one origin                  package.json, "exports", symlinks
async fetch                 cheap synchronous stat
```

Standardising either would have made the other non-conformant. So the spec defines **host
hooks** (abstract operations such as `HostLoadImportedModule`) and each host fills them in —
the same pattern ECMAScript uses for job queues and timers.

**2. They tried, and it failed.** There was an ES6 module-loader effort, later moved to
WHATWG. It could not reconcile browser and server requirements and was abandoned. So
"deliberately" is honestly "deliberately, after trying".

**3. The payoff is real.** Because *linking* semantics are host-independent, the same module
graph means the same thing in browsers, Node, Deno, Bun and every bundler. The static
structure is standardised; only "where the bytes come from" is not.

**Direct consequence:** this is why `moduleResolution` exists as a TypeScript option at all.
TS must model *the host's* resolution to typecheck imports, and there are several hosts —
hence `node16`, `nodenext`, `bundler`. Lesson **3.2**.

## Interlude — "loader" means three different things

*(Student question: "so webpack is a browser loader and swc is a server loader?" — no.)*

```
RUNTIME LOADER   Part of the host. Not a tool you install.
                 Given a specifier + importer: find, fetch, hand to the engine.
                 Browser: the browser (URL + HTTP).
                 Node:    Node (node_modules walk + "exports"/"imports" + "type").
                 <- THIS is what ES2015 declined to standardise.

BUNDLER          Build-time. webpack, Rollup, esbuild, Vite, Parcel.
                 Resolves the whole graph ahead of time and emits output that
                 needs no runtime loading. Implements its OWN resolver.

TRANSPILER       swc, Babel, tsc. Rewrites syntax. Does not resolve or load.
```

**The terminology trap:** webpack calls its own transform plugins "loaders"
(`babel-loader`, `css-loader`). Entirely different meaning — they transform file contents and
never resolve anything. This is a very common source of confusion, and it is webpack's fault.

**Real pluggable loaders do exist**, on both sides:

- **Node — module customization hooks** (`module.register()`, formerly `--loader`). This is how
  `tsx`, `ts-node/esm` and `@swc-node/register` work: they register a hook so that when Node
  asks to load a `.ts` file, it is transformed first. Note swc's position here — it is the
  *transformer* called *inside* Node's loader hook, not a loader itself.
- **Browser — import maps.** A web standard supplying bare-specifier → URL mappings, since
  browsers have no `node_modules`.

**Why this matters for monorepos:** because no loader was standardised, **every tool carries
its own resolver** — Node's, webpack's, Vite's, esbuild's, Jest's, `tsc`'s. Separate
implementations of a job with no standard, so they routinely disagree about the same import.
"Vite resolves it but `tsc` doesn't", "works in dev, 404s in the Docker build", "Jest can't
find the workspace package" — every one is two resolvers reading the same `package.json`
differently. It is also why `moduleResolution: "bundler"` exists: a formal admission that
these resolvers differ.

## Why `"exports"` is meaningless in a browser

*(Student question, and the sharpest one of the session.)*

`"exports"` and `"imports"` are fields **inside a `package.json`**. For a browser to use them,
that file would have to exist somewhere it can reach — and in a browser, "somewhere it can
reach" means *a URL fetched over the network*. There is no filesystem, and in 2015 there was
no concept of a package at all.

Resolving `import _ from 'lodash'`, side by side:

```
NODE — a filesystem walk, all local            BROWSER — no algorithm exists
  stat /app/src/node_modules/lodash   miss       'lodash' is not a URL, and not
  stat /app/node_modules/lodash       hit        relative to one
  read .../lodash/package.json                   -> TypeError: Failed to resolve
  consult "exports" -> "./lib/index.js"             module specifier "lodash"
  -> /app/node_modules/lodash/lib/index.js
  (four calls, microseconds each)              Bare specifiers were simply illegal.
```

Now price Node's algorithm over HTTP — demo page 5 measures exactly this, with a 50 ms
simulated round trip (measured: 52 ms):

```
GET /simulate/src/node_modules/greeter/package.json  -> 404   ~50ms wasted
GET /simulate/node_modules/greeter/package.json      -> 200   ~50ms, parse "exports"
GET /simulate/node_modules/greeter/index.js          -> 200   ~50ms
  TOTAL ~150ms to resolve ONE bare specifier
  ...and that file's own imports restart the sequence. Waterfall depth = tree depth.
```

**Node's algorithm assumes failed lookups are nearly free.** A `stat` on a missing path costs
microseconds; over HTTP it is a full round trip you must wait for. The same algorithm that is
elegant on a filesystem is pathological over a network.

Import maps invert the authority to fit the constraint:

|  | `"exports"` | import map |
|---|---|---|
| Who decides | the **package** | the **page** |
| When | at resolution time, after the package is found | upfront, before anything is fetched |
| Requires | a filesystem to search | nothing |

Same problem — mapping a name to a location — under opposite constraints. Seen this way,
`"exports"` stops looking like Node trivia and starts looking like one branch of a fork.

## Node's own problem: `.js` already meant CommonJS

> **`.js` already meant CommonJS**, across millions of deployed packages.

Node could not reinterpret it, could not break it, and could not ask the ecosystem to wait.
Two camps formed: signal the mode with a new **extension** (`.mjs`/`.cjs`), or with a
**`package.json` field** (`"type": "module"`). Node shipped **both** — which is exactly why
the rules feel doubled: `.mjs`/`.cjs` always win, `"type"` decides what `.js` means.

The doubling is not redundancy. It is two camps in a long argument, both of whom got their
way.

Read Node's module design as a **compatibility engineering problem, not a language design
one** — it looks strange only when judged as the latter.

## Why not just detect the syntax?

The obvious-looking alternative to extensions and a `"type"` field: parse the file, and if it
contains `import`/`export`, treat it as ESM. Node rejected this as the *primary* signal for
four reasons of quite different kinds.

1. **A file containing neither is unresolvable.** `console.log('hello')` has no signal — and
   the choice still matters, because the modes differ in strict mode, `this`
   (`module.exports` vs `undefined`), and the presence of `__dirname` / `require`.
2. **Spec-level chicken-and-egg.** ECMAScript has two grammars, `Script` and `Module`, and the
   host must choose one *before* parsing. `await` is a legal identifier in Script and reserved
   at top level in Module. You cannot parse the file to learn how to parse the file.
3. **Fragility.** Deleting the last `export` from a file would silently convert it to
   CommonJS, changing strict mode, `this`, and the availability of `require`. A cosmetic
   refactor would change the language the file is written in.
4. **Every tool must agree.** Bundlers, `tsc`, ESLint, and editors would each reimplement the
   same heuristic identically, forever. A filename or a field is trivially readable by all.

**But detection does exist — as a strictly bounded fallback.** *Module syntax detection*
(experimental in Node 21, unflagged since Node 22.7) applies only when there is no explicit
signal. Verified on Node v24.18.0:

```
(1) .js with ESM syntax, no package.json anywhere
    -> ran as ESM.                     detection worked

(2) same files, package.json says "type": "commonjs"
    -> SyntaxError.                    the SIGNAL wins; detection gets no vote

(3) a file with no import/export, no package.json
    -> this === module.exports: true
       typeof __dirname       : string ... fell back to CommonJS
```

The principle to steal: **declarations first, heuristics strictly last, and never as an
override.** Contrast with `cjs-module-lexer`, a heuristic that *is* authoritative — and which
produces the three failure modes catalogued below. Syntax detection is the design made after
that lesson was learned.

## Why it took five years, specifically

*(Student question: "I got it in substance, but not *why* it took 5 years.")*

```
2015  ES2015 modules standardised (syntax only)
2017  Node 8.5   --experimental-modules, .mjs only
 ...             the original implementation is discarded and rewritten
                 by the Modules Working Group
2019  Node 12    "type": "module" and conditional "exports" land
2019  Node 13.2  ESM unflagged
2024  Node 22.12 require(esm) unflagged
```

Not one reason — five, compounding:

1. **The design argument was genuinely hard and genuinely contentious.** `.mjs` versus
   `"type"` split the community for years. Node shipped `.mjs` first, then added the field.
   Both sides had real breakage arguments; this was not bikeshedding.
2. **The first implementation was thrown away.** Node 8.5 (2017) shipped one design; it was
   later replaced wholesale by a new implementation from the Modules Working Group. Roughly
   two of the five years went into a restart.
3. **The primitives did not exist yet.** Dynamic `import()` and `import.meta` only reached the
   standard in **ES2020**; top-level await in **ES2022**. Node could not finish a module system
   whose essential escape hatches were still being designed at TC39.
4. **Interop had to be invented, not merely implemented.** Whether CJS should be importable
   from ESM *at all* was contested, and the named-export detection approach (the lexer) had to
   be researched and built. There was no prior art to copy.
5. **Node was terrified of becoming Python 3.**

Point 5 is the real answer underneath the other four. A hard ESM cutover would have split the
ecosystem into two incompatible halves exactly as Python 2→3 did — and Node's leadership
watched that happen in real time and resolved not to repeat it. Every conservative choice
(opt-in, doubled signalling, CJS remaining the default forever, `require(esm)` arriving
eventually rather than never) is that fear expressed as engineering.

**Slow was the goal, not the failure.**

## The transpiler interregnum

Throughout those five years Babel and TypeScript let people write `import`/`export` *now* by
compiling down to CommonJS. A generation wrote ESM syntax while running CJS, and learned
semantics that were really **Babel's emulation** of ESM.

That emulation needed a marker for "this CJS object came from ESM source" and invented
**`__esModule`** — not in any standard, existing solely because transpilers needed it.
`esModuleInterop` is TypeScript's participation in that convention.

> This is the historical root of the student's placement answer. Reaching for
> `esModuleInterop` was the model that *was* correct for most of the last decade of
> real-world JS. A historically well-founded wrong answer.

## What the retrofit cost

- **`exports` maps with conditions** (`"import"` / `"require"`) — lesson 1.3, and the reason
  `arethetypeswrong` exists (4.4).
- **The dual package hazard** — the same package loaded twice in one process, once as CJS and
  once as ESM. Two module instances, two sets of class identities: `instanceof` returns
  `false` between objects of "the same" class, and every module-level singleton or cache
  silently doubles. A nasty, real production incident shape.
- **Why "just use ESM" was never available** — you can be ESM-only only if every consumer can
  load you. Before Node 22.12 a CJS consumer simply could not `require` you. Module format was
  dictated by *consumers'* constraints, not the author's preference.

## History — recap

1. **`.js` already meant CommonJS.** Node's entire module design is downstream of that one
   compatibility constraint, not of language-design taste.
2. **Every ergonomic property of CJS was bought by surrendering a static one** — and static
   analysis is what all monorepo tooling runs on.
3. **CJS's synchrony broke the browser**, which is why bundlers exist; and because the server
   or the build assembled the page, **nobody ever asked the browser to resolve anything** until
   2015.
4. **ES2015 standardised linking, not loading**, because browser and server resolution are
   irreconcilable — so every tool now carries its own resolver, and they disagree.
5. **Two signalling mechanisms shipped, not one**; syntax detection was rejected as
   authoritative and later admitted only as a bounded fallback.
6. **Five years of transpiled ESM-over-CJS** produced `__esModule` and `esModuleInterop` — and
   the layer confusion this lesson opened with.
