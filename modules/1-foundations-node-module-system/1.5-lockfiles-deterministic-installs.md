## Placement context

Fifth and last lesson of Module 1, delivered the same day as 1.4. 1.4 ended on two things the
package manager decides for you: which versions, and where they land. Its "bug two" was an npm
lockfile remembering a placement. This lesson is about the lockfile as an artefact: what it
records, what it deliberately does not, and the habits that keep installs reproducible.

**Goal stated at the start:** read a `pnpm-lock.yaml`, predict what `pnpm install` will change
in a given situation, and explain why "delete the lockfile and reinstall" is the most expensive
fix in the toolbox.

---

## Concept — intent versus fact

`package.json` records **intent**: `"semver": "^7.5.0"` means any 7.x at or above 7.5.0, a
promise about compatibility written by you. The lockfile records **fact**: on this date, with
this registry, that range resolved to `7.5.4`, whose tarball has this hash, and which pulled in
these exact versions of its own dependencies. A constraint, and one solution to it.

Determinism is the property that the same two files produce the same dependency graph on any
machine, on any day. Without the lockfile you hold only the constraints and must re-solve them,
and the solution changes whenever the registry does.

## Mechanism — anatomy of `pnpm-lock.yaml`

One package depending on `semver 7.5.4` and `is-odd 3.0.1`, trimmed:

```yaml
lockfileVersion: '9.0'

settings:
  autoInstallPeers: true
  excludeLinksFromLockfile: false

importers:
  .:
    dependencies:
      is-odd:
        specifier: 3.0.1
        version: 3.0.1
      semver:
        specifier: 7.5.4
        version: 7.5.4

packages:
  is-odd@3.0.1:
    resolution: {integrity: sha512-CQpnWPrDwmP1+SMHXZhtLtJv90yiyVfluGsX5iNCVkrhQtU3TQHsUWPG9wkdk9Lgd5yNpAg9jQEo90CBaXgWMA==}
  semver@7.5.4:
    resolution: {integrity: sha512-1bCSESV6Pv+i21Hvpxp3Dx+pSD8lIPt8uVjRrxAUt/nbswYc+tK6Y2btiULjd4+fnq15PX+nqQDC7Oft7WkwcA==}
    hasBin: true
  lru-cache@6.0.0: ...
  yallist@4.0.0: ...

snapshots:
  is-odd@3.0.1:
    dependencies:
      is-number: 6.0.0
  semver@7.5.4:
    dependencies:
      lru-cache: 6.0.0
  lru-cache@6.0.0:
    dependencies:
      yallist: 4.0.0
```

| Section | Records | Used for |
|---|---|---|
| `importers` | per workspace package: each declared dep's `specifier` (copied from the manifest) and resolved `version` | the join between intent and fact; what `--frozen-lockfile` compares |
| `packages` | every distinct `name@version` with its `integrity` hash | supply chain: the exact bytes reviewed when the dep entered the graph |
| `snapshots` | the resolved graph: who depends on which exact version; keys may carry a peer suffix like `typescript-eslint@8.72.1(eslint@9.39.5)(typescript@5.9.3)` | reconstructing the layout; peer identity (2.4) |
| `settings` | the few settings that change *what the graph is* | refusing to reuse a lockfile produced under different rules |

### In a workspace

One lockfile at the root, every package inside it under `importers`:

```yaml
importers:
  .:
    devDependencies:
      typescript: { specifier: ^5.9.2, version: 5.9.3 }
  packages/a:
    dependencies:
      is-odd: { specifier: 3.0.1, version: 3.0.1 }
  packages/b:
    dependencies:
      is-number: { specifier: 7.0.0, version: 7.0.0 }
```

There are no per-package lockfiles in a pnpm workspace. `pnpm install --filter` still reads this
one file, and `turbo prune` (8.3) carves a subset of it for Docker.

### What the lockfile does not pin

- **The layout.** Zero mentions of `nodeLinker` or hoisting. 1.4's demo produced the isolated
  and the hoisted layout from one lockfile. pnpm derives layout from lockfile plus settings;
  npm's `package-lock.json` records the physical tree, which is why npm did not re-hoist in
  1.4's bug two.
- **The registry.** `resolution` holds an integrity hash, not a URL. Point pnpm at a mirror and
  the file stays valid; the hash is what is checked.
- **Node's version, the OS, the store.** The lockfile is a graph.
- **Your ranges.** It copies them as `specifier` but does not enforce them. Ranges matter again
  the moment something is re-resolved.

## Five experiments

**1. Widen a range, reinstall.** `"semver": "7.5.4"` → `"semver": "^7.5.0"`.

```
semver installed: 7.5.4
lockfile diff:
  <         specifier: 7.5.4
  >         specifier: ^7.5.0
```

Only the `specifier` line changed. The locked `7.5.4` satisfies the new range, so it stays.
**Changing a range upgrades nothing by itself.**

**2. Delete only the lockfile, keep `node_modules`.**

```
semver installed: 7.5.4
```

Nothing happened: pnpm keeps a private copy at `node_modules/.pnpm/lock.yaml` and rebuilt the
root file from it. This is why "I deleted the lockfile and it was fine" comes from laptops and
never from CI, which starts from an empty checkout.

**3. Delete the lockfile and `node_modules`.**

```
semver installed: 7.8.5          (latest on the registry today)
  < semver@7.5.4   + lru-cache@6.0.0 + yallist@4.0.0
  > semver@7.8.5   (no dependencies)
```

Every range re-solved to the newest satisfying version at this instant. One direct dependency
moved three minors and dropped two transitive packages. At the scale of a real graph this is
hundreds of versions nobody chose, reviewed, or tested together. The lockfile is the one
artefact that encodes "this combination was tested"; regenerating it discards that.

Observed while building the demo: when another importer pins the same package exactly, a
regenerated lockfile reuses that version for the range too, and the diff is empty. pnpm prefers
versions already in the graph. Another reason the laptop report is unreliable.

**4. The frozen install.** `^7.6.0` in the manifest, `7.5.4` locked:

```
[ERR_PNPM_OUTDATED_LOCKFILE] Cannot install with "frozen-lockfile" because pnpm-lock.yaml
is not up to date with <ROOT>/package.json
Note that in CI environments this setting is true by default.
  specifiers in the lockfile don't match specifiers in package.json:
  - semver (lockfile: 7.5.4, manifest: ^7.6.0)
```

`--frozen-lockfile`: install exactly the locked graph; if the manifests disagree, fail rather
than resolve. pnpm enables it when it detects CI. The comparison is **textual**, specifier
against manifest string, which is why `^3.0.0` versus `3.0.1` fails even though `3.0.1`
satisfies the range.

**5. Integrity.** One character flipped in `is-odd`'s hash, frozen install from empty
`node_modules`:

```
[ERR_PNPM_TARBALL_INTEGRITY] Got unexpected checksum for ".../is-odd-3.0.1.tgz".
The downloaded tarball does not match the integrity recorded in the lockfile. pnpm will
not silently overwrite the locked integrity — that would defeat the lockfile's protection
if a registry or proxy is serving tampered content.
```

The lockfile is a security boundary. pnpm 11 layers "supply-chain policies" on top (the
`Lockfile passes supply-chain policies` line in every run above); that is a *different* check
with a different error, see the check-in below.

## Habits

1. **Commit the lockfile, always**, libraries included. The old "libraries should not commit
   lockfiles" advice concerns a *published* package's consumers, who never see a workspace
   lockfile.
2. **Pin the package manager** via `packageManager` in the root `package.json`; different
   pnpm versions write the lockfile differently.
3. **Update one thing**: `pnpm update semver`, or `pnpm update --latest semver`. `pnpm outdated`
   to see what is behind; `pnpm dedupe` to collapse accumulated duplicates.
4. **Resolve lockfile conflicts by running `pnpm install` on the conflicted file**, which pnpm
   knows how to merge. Never by regenerating.
5. **Let CI freeze.** The default is right.

## Check-in question — **ANSWERED**

A PR changes only `packages/api/package.json`:

```
-  "zod": "^3.22.0"
+  "zod": "^3.23.0"
```

The lockfile is untouched and resolves `zod` to `3.22.4`. The registry's latest 3.x is
`3.25.76`.

**Part 1:** CI runs `pnpm install` on a fresh checkout. What happens, and why?
**Part 2:** the teammate runs `pnpm install` locally, it succeeds, they commit the lockfile
change. Which `zod` is now locked, and does the diff touch anything other than `zod`'s lines?

**Student's answer, Part 1:** *"CI fails because of the supply chain policy: package's version
does not match the lock's one, and pnpm enables the frozen lockfile behavior when it detects a
CI."*

**Verdict: right conclusion, wrong label.** Actual run:

```
✓ Lockfile passes supply-chain policies (verified 877ms ago)
[ERR_PNPM_OUTDATED_LOCKFILE] Cannot install with "frozen-lockfile" because pnpm-lock.yaml
is not up to date with <ROOT>/packages/api/package.json
  - zod (lockfile: ^3.22.0, manifest: ^3.23.0)
```

The supply-chain policy check **passed**; it is a separate pnpm 11 feature (release age,
provenance). The failure is `ERR_PNPM_OUTDATED_LOCKFILE`, the specifier comparison. Two codes,
two parts of pnpm, two fixes ("commit your lockfile" vs "this package is too new"). Also: what
mismatched is the *specifier*, `^3.22.0` against `^3.23.0`, a range against a range.

**Recurring pattern flagged:** attaching a failure to the nearest familiar line of output rather
than to the error code. Error codes were the diagnostic lever in 1.2 (`MODULE_NOT_FOUND` vs
`ERR_MODULE_NOT_FOUND`) and 1.3 (`ERR_PACKAGE_PATH_NOT_EXPORTED`); re-test in 8.4.

**Student's answer, Part 2:** *"new locked version is 3.23.0. It also affected the lockfile,
exact version and allowed range."*

**Verdict: wrong version; diff half described.** Actual run:

```
zod installed: 3.25.76
  <         specifier: ^3.22.0        >         specifier: ^3.23.0
  <         version: 3.22.4           >         version: 3.25.76
  <   zod@3.22.4:                     >   zod@3.25.76:
  <     resolution: {integrity: ...}  >     resolution: {integrity: ...}
  <   zod@3.22.4: {}                  >   zod@3.25.76: {}
```

A range re-resolves to the **highest** satisfying version (pnpm's default `resolutionMode`;
npm and yarn agree), not the lowest. `^3.23.0` does not mean "3.23.0"; it means "3.23.0 up to
but excluding 4.0.0, newest wins today". Wanting exactly 3.23.0 is spelled `3.23.0`.

The diff: `importers` changes in two lines (specifier and version, as the student said), **and**
the `packages` and `snapshots` entries for `zod@3.22.4` are replaced by entries for
`zod@3.25.76` with a new integrity hash. Nothing outside `zod` moves, because `zod` has no
dependencies and every unchanged specifier keeps its locked version. With `semver` instead,
`lru-cache` and `yallist` would also have left the graph (experiment 3).

**Three things resolve a range, and only one is you:** the range sets floor and ceiling, the
registry's state that day sets what exists, the resolver's mode picks highest. The lockfile is
the only place that moment is written down.

## Key takeaways

1. `package.json` is intent (ranges); the lockfile is fact (one resolved graph, hashed).
2. `importers` joins the two per workspace package; `packages` holds integrity; `snapshots`
   holds the graph; `settings` guards reuse.
3. The lockfile does not pin the layout, the registry, Node, or the store.
4. Changing a range changes nothing while the locked version still satisfies it.
5. Deleting the lockfile with `node_modules` present changes nothing either: pnpm keeps a
   private copy. Deleting both re-solves every range to the newest version today.
6. `--frozen-lockfile` compares specifiers textually and is on by default in CI. It is the
   mechanism that turns "forgot to commit the lockfile" into a fast red build.
7. Integrity hashes make the lockfile a security boundary; pnpm refuses tampered tarballs.
8. Ranges resolve to the **highest** satisfying version. `^3.23.0` is not 3.23.0.
9. Commit the lockfile, pin the package manager, update one entry at a time, let pnpm merge
   conflicts, never regenerate.
10. Error codes are the diagnosis. `ERR_PNPM_OUTDATED_LOCKFILE` and the supply-chain policy
    line are different checks with different fixes.

## Failure modes of lesson 1.5, by loudness

| Failure | When | Symptom | Where seen |
|---|---|---|---|
| Manifest and lockfile disagree | CI install | `ERR_PNPM_OUTDATED_LOCKFILE`, names the dep | experiment 4; check-in Part 1; exercise 1.5-b |
| Tampered or republished tarball | install | `ERR_PNPM_TARBALL_INTEGRITY` | experiment 5 |
| Range bumped expecting a version bump | never fails | nothing changes; or, on re-resolution, far more changes than expected | experiment 1; check-in Part 2 |
| Lockfile regenerated "to fix a conflict" | never fails | hundreds of silent version changes, transitive graph reshaped | experiment 3; demo break 2 |
| No lockfile committed | never fails | every machine and every CI run installs a different graph | the reason the file exists |

One loud mode that is a gift, one loud mode that is a shield, three quiet ones that are the
whole reason to care.
