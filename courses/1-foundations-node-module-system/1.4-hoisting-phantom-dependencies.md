## Concept — two layers, two moments

```
install time   the package manager decides WHERE each package goes on disk
require time   Node walks the directories it finds, with no memory of who put them there
```

**Hoisting** is an install-time decision: place each package as high in the tree as possible
so one copy serves everyone below it. **A phantom dependency** is a require-time consequence:
a package your code imports that your `package.json` never declared, reachable only because
hoisting happened to put it above you.

Why npm started hoisting: before npm 3 (2015), `node_modules` was nested exactly as declared.
Faithful, and catastrophic: the same package duplicated dozens of times, and paths deep enough
to break Windows. npm 3 flattened the tree. The 1.2 walk made that safe for resolution, since a
package one level up is still found. It also made every hoisted package visible to everyone.
Nobody designed phantom dependencies; they are the shadow of a performance fix.

## Mechanism — the same install, two layouts

One app, one declared dependency. `is-odd` depends on `is-number`; the app never mentions it.

```json
{ "name": "app", "dependencies": { "is-odd": "3.0.1" } }
```

```
=== npm ===
node_modules/
  is-number/        ← hoisted; the app never asked for it
  is-odd/

require('is-number')(4)  -> true   from <app>/node_modules/is-number/index.js
```

Works, silently. The identical manifest installed with pnpm:

```
=== pnpm ===
node_modules/
  is-odd -> .pnpm/is-odd@3.0.1/node_modules/is-odd           ← the ONLY entry
  .pnpm/
    is-odd@3.0.1/node_modules/
      is-odd/                                               ← the real files
      is-number -> ../../is-number@6.0.0/node_modules/is-number   ← its dep, as a SIBLING
    is-number@6.0.0/node_modules/
      is-number/
    node_modules/
      is-number                                             ← hoisted HERE (see below)

require('is-number')  -> MODULE_NOT_FOUND
require('is-odd')(3)  -> true
from inside is-odd, is-number lives at
  <app>/node_modules/.pnpm/is-number@6.0.0/node_modules/is-number/index.js
```

Two walks, both pure 1.2:

- **The app's walk** starts at `<app>/` and tries `<app>/node_modules/is-number`. Only `is-odd`
  is there. It climbs to the root and fails.
- **The library's walk**: `is-odd` is reached through a symlink, Node resolves it to its real
  path `.pnpm/is-odd@3.0.1/node_modules/is-odd/`, so the first candidate directory is
  `.pnpm/is-odd@3.0.1/node_modules/`, where pnpm placed a symlink to exactly the `is-number`
  version `is-odd` declared. Found on the first try.

pnpm's layout is the three 1.2 facts arranged on purpose: the real-path rule decides where a
package's walk starts; nearest-wins means a sibling symlink is found first; up-only means the
app can never descend into `.pnpm/`. **Strictness is not a check pnpm performs; it is a
property of the directory shape.**

### pnpm's own hoisting, and the escape hatches

There *is* hoisting in pnpm: `.pnpm/node_modules/is-number`. The default `hoistPattern` is
`*`, into that hidden folder, which is on the walk of every package inside `.pnpm/` but not on
the walk of your own code. Translation: your dependencies may still phantom-reach each other,
because too many published packages rely on it and pnpm would be unusable otherwise; your
own packages cannot. The escape hatches, mild to total:

| Setting | Effect | What you trade back |
|---|---|---|
| `publicHoistPattern: ['name']` | hoists matching packages into the root `node_modules` | phantom access to those names, everywhere |
| `shamefullyHoist: true` | hoists everything into the root `node_modules` | the whole guarantee; npm's reach with pnpm's symlinks |
| `nodeLinker: hoisted` | produces npm's flat layout, no `.pnpm` | everything, including the identity guarantees of 1.2 |

Observed on pnpm 11.9: these are read from `pnpm-workspace.yaml`; a `node-linker=hoisted` line
in `.npmrc` was ignored, and switching the linker did not relink an existing `node_modules`
without a clean reinstall. `publicHoistPattern` defaults to empty since pnpm 10.

## Why phantoms are bugs, not style

The app above works. The lesson is what "works" hides. An npm workspace, two packages: `a`
uses `is-number` without declaring it; `b` happens to declare a newer one.

```
packages/a/package.json   dependencies: { "is-odd": "3.0.1" }       (needs is-number ^6)
packages/b/package.json   dependencies: { "is-number": "7.0.0" }
```

```js
// packages/a/index.js
const isNumber = require('is-number')             // never declared by a
```

```
node_modules/is-number                       ← 7.0.0, hoisted from b
node_modules/is-odd/node_modules/is-number   ← 6.0.0, nested because of the conflict

a sees is-number 7.0.0
is-odd uses is-number 6.0.0
```

**Bug one: you do not control the version.** `a` believes it is borrowing the `is-number` that
`is-odd` brought along. It gets `b`'s major 7, chosen by the conflict-resolution order of an
unrelated package. No constraint anywhere states what `a` needs, so no tool can flag it.
pnpm's hoisted linker, given the same manifests, put version 6 at the root instead (demo).
Which version a phantom gets is an implementation detail of the hoisting algorithm.

**Bug two: you do not control existence.** `b` refactors and drops its dependency. `a` does
not change a line:

```
node_modules/is-odd/node_modules/is-number   ← only copy left, nested, out of a's reach

Error: Cannot find module 'is-number'
Require stack:
- <ws>/packages/a/index.js
```

npm did **not** re-hoist version 6 to the root; the lockfile remembers the previous placement,
so the layout is a function of install *history*, not only of current declarations. The diff
that broke `a` touched a different package and mentions none of `a`, `is-odd`, or a version.

**Bug three: two copies.** The conflict nested a second `is-number`. By 1.2's identity rule,
two module instances. Harmless for `is-number`; for anything with state or classes, this is
the "two Reacts" family, and hoisting conflicts are its most common cause.

**Bug four: the monorepo amplifier.** In a hoisted workspace every package's dependencies land
in the root `node_modules`, which is on every package's walk, so every package can import
anything any sibling declared. Tests pass locally for years. Then one package is built in
Docker from a pruned lockfile (8.3), deployed with `pnpm deploy`, or consumed outside the
repo, and only its own declarations come along. The production failure is `MODULE_NOT_FOUND`
for a module that was never in its `package.json`, and the first suspect is always the build.

The root cause of all four is one sentence: **the thing that decided the layout read
`package.json`, and the thing that read the layout did not.** Node has no idea what you
declared. Hoisting severs "what I said I need" from "what I can reach", and every phantom bug
is that gap discovered late, by someone else's change.

---

## What to do about it, today

In a pnpm workspace the layout does most of the work: a phantom import in your own code fails
on the first `pnpm install`, with the 1.2 require stack naming the package at fault. Three
habits finish the job:

1. `MODULE_NOT_FOUND` naming a workspace package in its stack means *that package forgot a
   declaration*. Never "install it at the root".
2. Keep the root `package.json` to tooling. Anything declared there is reachable from every
   package: hoisting by hand.
3. When a third-party dependency is itself broken by strictness, fix it narrowly with
   `publicHoistPattern` for that name, not with `shamefullyHoist`.

Lesson 2.2 covers the store and the `.pnpm` layout in full; 7.4 adds lint rules that catch
undeclared imports at review time.

## Check-in question — **ANSWERED**

A pnpm workspace, default settings:

```
root/
  package.json               devDependencies: typescript, eslint
  packages/ui/package.json   dependencies: react
  packages/app/package.json  dependencies: "@demo/ui": "workspace:*"
  packages/app/src/main.ts   import React from 'react'      ← not declared by app
```

**Part 1:** does `react` resolve from `packages/app/src/main.ts`? Walk the candidates.
**Part 2:** a teammate proposes adding `react` to the **root** `package.json` "so every package
has it". Does the import resolve, and what is wrong with it as a fix?

**Student's answer, Part 1:** *"it does not resolve. because react wouldn't exist in
`/.pnpm/app/node_modules/` (no symlink to actual files). If app was to declare it, it would be
at `/.pnpm/app/node_modules/react`, symlinked to `/.pnpm/react/node_modules/`."*

**Verdict: conclusion right, layout wrong.** Built and run:

```
node_modules/.pnpm/
  react@19.1.0
  typescript@5.9.3          ← only REGISTRY packages live in the virtual store
packages/app/node_modules/
  @demo/ui -> ../../../ui   ← workspace packages stay in place, linked by relative symlink
packages/ui/node_modules/
  react -> ../../../node_modules/.pnpm/react@19.1.0/node_modules/react

candidates from app:
  <root>/packages/app/src/node_modules
  <root>/packages/app/node_modules       ← only @demo/ui
  <root>/packages/node_modules
  <root>/node_modules                    ← only typescript
react -> MODULE_NOT_FOUND
```

Corrections recorded:

- `.pnpm/` is the **virtual store**: it holds what pnpm *fetched*. A workspace package was
  never fetched, so it is never copied there; it stays in `packages/` and is consumed in place
  through a relative symlink, exactly as in the 1.2 demo. The student said afterwards that this
  distinction had not been clear. **Re-test in 2.2** (store vs virtual store vs workspace
  links).
- If `app` declared `react` it would appear at `packages/app/node_modules/react`, a symlink to
  `node_modules/.pnpm/react@19.1.0/node_modules/react`. The **version in the store directory
  name** is what lets two versions coexist, which Part 2 turns on.

**Student's answer, Part 2:** *"it would make the import resolve, by the walk-up mechanism.
But then, every package would have it and it forces the same version everywhere."*

**Verdict: resolution right, diagnosis backwards.** It forces nothing; that is the problem.

```
root declares react 19.1.0, ui declares react 19.1.0
  app (via root) -> .pnpm/react@19.1.0/node_modules/react
  ui             -> .pnpm/react@19.1.0/node_modules/react     one store dir, ONE instance

ui upgrades to 19.2.0, as it is entitled to
  app (via root) -> .pnpm/react@19.1.0/node_modules/react
  ui             -> .pnpm/react@19.2.0/node_modules/react     two store dirs, TWO instances
```

Two React instances in one process is the "Invalid hook call" error, and nothing in either
manifest says the two must agree. Alignment becomes a human discipline (2.5: syncpack,
catalogs; 2.4: peer dependencies). And the deeper objection: the root `node_modules` is on
every package's walk, so declaring there is hoisting by hand; `app` still uses `react` without
declaring it and breaks again the moment it is built alone. The fix is one line in
`packages/app/package.json`; whether `ui` should list `react` as a peer is the 2.4 question.

**Pattern across 1.2, 1.3, 1.4 check-ins:** conclusions increasingly right, mechanisms still
reconstructed from memory rather than traced. The exercises for this lesson are both
predict-then-verify for that reason.

## Key takeaways

1. Two layers: the package manager decides the layout at install time; Node walks it at
   require time with no knowledge of any manifest. Answer each question at its own layer.
2. Hoisting flattens the tree so one copy serves many. It is a 2015 performance fix whose side
   effect is that everything hoisted is reachable by everything below.
3. A phantom dependency is the gap between what a package can reach and what it declared.
   In a hoisted layout nothing on the machine shows you that gap.
4. Four bug classes: version chosen by someone else's conflict; existence removed by someone
   else's refactor; duplicate instances from nested conflicts; the monorepo amplifier that
   fails only when a package is built alone.
5. pnpm's isolated layout makes your own phantoms impossible by directory shape: real-path
   walk start, sibling symlinks for declared deps, up-only climb that never enters `.pnpm/`.
6. pnpm still hoists *inside* `.pnpm/node_modules` for your dependencies' sake. Your code is
   not on that path.
7. `.pnpm/` is the virtual store: fetched packages only, one directory per name@version.
   Workspace packages stay in place and are linked relatively.
8. `publicHoistPattern`, `shamefullyHoist`, `nodeLinker: hoisted`: each trades back a slice of
   the guarantee. Prefer the narrowest.
9. "Put it at the root so everyone has it" rebuilds the hoisted layout by hand and forces no
   alignment at all. Fix a phantom at the package that uses it.
10. Which version a phantom gets, and whether it survives an unrelated refactor, depends on
    the package manager's algorithm and on install history. Neither is yours.

## Failure modes of lesson 1.4, by loudness

| Failure | When | Symptom | Where seen |
|---|---|---|---|
| Phantom under isolated layout | first `pnpm install` | `MODULE_NOT_FOUND`, stack names the package | demo shipped state; exercise 1.4-b |
| Phantom lost to a sibling's refactor | next install after someone else's change | `MODULE_NOT_FOUND` in a package with no diff | npm workspace run above |
| Package built alone (Docker, `pnpm deploy`) | deploy time | `MODULE_NOT_FOUND` for a never-declared module | 8.3; exercise 1.4-b's solo install |
| Phantom changes version | never fails | different major, plausible behaviour | demo break 2 |
| Two instances from a nested conflict | never fails | state split, `instanceof` false, two Reacts | check-in Part 2 |

Two loud, three quiet. The loud ones are pnpm's gift; the quiet ones are what hoisting costs.
