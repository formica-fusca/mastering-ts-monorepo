## Syntax & semantics

All output below verified on Node v24.18.0.

### Live bindings — the silent one

The experiment: two counter modules that are **functionally identical** — one written as ESM,
one as CJS — imported side by side by a single consumer, which increments both and prints
them before and after.

```js
// counter.mjs  — ESM version
export let count = 0
export function inc() { count++ }
```

```js
// counter.cjs  — CJS version, same logic
let count = 0
exports.count = count            // a COPY of the value, taken right now
exports.inc = () => { count++ }
```

```js
// main.mjs  — the consumer. Imports BOTH and increments BOTH.
import { count, inc } from './counter.mjs'
import { createRequire } from 'node:module'

const require = createRequire(import.meta.url)   // no `require` in ESM — see Module scope
const cjs = require('./counter.cjs')

console.log('             ESM      CJS')
console.log('before inc()  ', count, '      ', cjs.count)
inc()
cjs.inc()
console.log('after  inc()  ', count, '      ', cjs.count)
```

Running `node main.mjs` prints:

```
             ESM      CJS
before inc()   0        0
after  inc()   1        0     <- the CJS reader never sees the increment
```

Both counters were incremented. Only the ESM reader observed it.

**Why.** `exports.count = count` copies the **value** at the moment that line runs. The copy
on the exports object has no relationship to the `count` variable afterwards, so
`cjs.inc()` bumps the internal variable and the exported copy stays behind. An ESM `import`
is not a copy — it is a **reference into the exporting module's scope**, so it reflects
whatever the exporter's variable currently holds.

**Imports are also read-only.** V8 treats an imported binding exactly like a `const`:

```js
// readonly.mjs
import { count } from './counter.mjs'
count = 99
```

```
count = 99
      ^
TypeError: Assignment to constant variable.
```

Only the owning module may write its own binding. (Note this is a *runtime* `TypeError`, not
a parse error — the module parses fine and throws when the line executes.)

**Live bindings do not survive the CJS boundary.** This is the part that surprises people, and
it is easy to get wrong even after understanding everything above. Node builds a CJS module's
named exports by **copying its properties once, after evaluation** — they are a snapshot, not
live bindings. So even a correctly-written getter cannot make `import { count }` update:

```js
// counter.cjs — a proper accessor, in the exact shape the lexer recognises
let count = 0
Object.defineProperty(exports, 'count', {
  enumerable: true,
  get: function () { return count },
});
exports.inc = () => { count++ }
```

```js
// probe.mjs
import { count, inc } from './counter.cjs'   // named import
import ns from './counter.cjs'                // default import (= module.exports)
console.log('named before:', count, '| default before:', ns.count)
inc()
console.log('named after :', count, '| default after :', ns.count)
```

```
named before: 0 | default before: 0
named after : 0 | default after : 1
      ^^^^^ stale                ^^^^^ live
```

**`import { x }` and `import ns from` are not interchangeable when the target is CJS.** One is
a post-evaluation snapshot; the other is the live `module.exports` object. They behave
identically almost always — which is precisely why the difference bites when it finally
matters.

Two footnotes worth keeping. The lexer recognises `Object.defineProperty` only in the exact
shape transpilers emit (`enumerable: true` plus a `function () {}` getter); an arrow-function
getter is **not** detected, so the named export vanishes entirely. And this is all a CJS-side
limitation: ESM-to-ESM imports *are* live, as the counter example above shows.

**Why this one is the worst of the lesson.** Every other failure in 1.1 either refuses to
start or hands you `undefined`. This one hands you **a number** — a stale, entirely plausible
number — and your program carries on computing with it. A cache that reports the wrong size,
a feature flag that reads as its startup value forever, a config object frozen at import time.
Nothing errors, so nothing points at the module system.

### Imports are hoisted

Two files. The dependency announces itself when its body runs:

```js
// side.mjs  — the dependency
console.log('  [side.mjs body ran]')
export const x = 1
```

```js
// main.mjs  — note the import is on line 3, NOT at the top
console.log('=== evaluation order ===')       // line 1
console.log('  [importer body starts]')       // line 2
import './side.mjs'                           // line 3
console.log('  [importer body ends]')         // line 4
```

`node main.mjs` prints:

```
  [side.mjs body ran]          <- FIRST, before main.mjs line 1
=== evaluation order ===
  [importer body starts]
  [importer body ends]
```

Import declarations are not statements executed in place. They are hoisted, and the entire
dependency subgraph evaluates before the importing module's body begins. Hence
`if (x) import 'y'` is a syntax error, and hence **dynamic `import()`** — Promise-returning,
legal in both CJS and ESM — is the escape hatch. Before Node 22.12 it was the *only* way for
CJS to load ESM.

### Module scope

**Two separate programs**, one per module system, each printing what its own scope contains.

```js
// scope.mjs
console.log('typeof this        :', typeof this)
console.log('import.meta.dirname:', typeof import.meta.dirname)
console.log('typeof __dirname   :', typeof globalThis.__dirname)
```

```js
// scope.cjs
console.log('this === module.exports?', this === module.exports)
console.log('typeof __dirname        :', typeof __dirname)
```

```
$ node scope.mjs                      $ node scope.cjs
typeof this        : undefined        this === module.exports? true
import.meta.dirname: string           typeof __dirname        : string
typeof __dirname   : undefined
```

ESM is always strict mode. `this` is `undefined` at module top level — in CJS it is
`module.exports`. `__dirname`, `__filename`, `require`, `module` and `exports` are all absent
from ESM. Replacements: `import.meta.url`, `import.meta.dirname` / `import.meta.filename`
(Node 20.11+), and `createRequire(import.meta.url)` when `require` is genuinely needed — as
used in the live-bindings example above.

### Top-level await, and why it gates `require(esm)`

Two ESM modules, identical except that one awaits at the top level, and a **CommonJS** file
that tries to `require()` each of them:

```js
// plain.mjs
export const ready = 'no TLA'
```

```js
// tla.mjs
await new Promise((r) => setTimeout(r, 1))   // top-level await
export const ready = 'with TLA'
```

```js
// main.cjs  — CommonJS requiring ESM
try { console.log('require plain.mjs ->', require('./plain.mjs').ready) }
catch (e) { console.log('require plain.mjs ->', e.code) }

try { console.log('require tla.mjs   ->', require('./tla.mjs').ready) }
catch (e) { console.log('require tla.mjs   ->', e.code) }
```

`node main.cjs` prints:

```
require plain.mjs -> no TLA
require tla.mjs   -> ERR_REQUIRE_ASYNC_MODULE
```

Top-level `await` makes a module's **evaluation asynchronous**. `require()` is synchronous and
must return a value, so a module that cannot finish evaluating synchronously cannot be
`require`d **by construction**. Not a limitation Node chose — the 2009 decision still binding.

### Mandatory extensions

Relative specifiers need the real filename: `./util.js`, not `./util`. Node does no extension
guessing. This is why `moduleResolution: "nodenext"` makes you write `.js` in TypeScript
source whose file on disk is `.ts` — **the specifier describes the output**, not the input.
Settled in **3.2**.

## Concept — *when* are a module's exports known?

The syntax difference (`require`/`module.exports` vs `import`/`export`) is the least
interesting part. The real difference is **at what point in time a module's export names
exist**.

**CommonJS** predates any language-level module standard. A CJS module is a function body
Node calls, handing it an empty `exports` object. Whatever sits on that object when the
function returns *is* the module's exports. It is a runtime value: mutable, computable,
replaceable.

```js
// Legal, idiomatic CommonJS.
if (process.env.LEGACY) {
  module.exports = require('./v1')
} else {
  module.exports = require('./v2')
}
```

**ESM** is static by design. `import`/`export` are syntax, not function calls, and are only
allowed at the top level. That constraint is what lets an engine build the entire module
graph and wire every binding *before executing a single line of anyone's code*.

```
CommonJS                          ESM
────────                          ───
resolve  ──┐                      parse       (find all import/export syntax)
load     ──┤ interleaved,         instantiate/link  (resolve every binding —
execute  ──┘ one module at a time                    THROWS HERE if a name is missing)
                                  evaluate    (now, finally, run code)
   ▲                                  ▲
exports exist only AFTER          export names must be known BEFORE
this step                         this step
```

The collision: to satisfy `import { formatDate } from '@acme/utils'`, ESM must know at
**link time** that `formatDate` is an export. If `@acme/utils` is CommonJS, its exports
don't exist until **evaluate time**. The information ESM needs, by its own rules, does not
yet exist.

## Mechanism — `cjs-module-lexer`

Node bridges the gap with a deliberate hack. When an ESM file imports a CJS file, Node runs
the CJS **source text** through
[`cjs-module-lexer`](https://github.com/nodejs/cjs-module-lexer) — a tiny, very fast parser
that does **not execute the code**. It scans for a fixed set of recognisable export
patterns and reports the names found. Node synthesizes those as named exports.

Recognised shapes include:

```js
exports.formatDate = ...                          // ✓
module.exports = { formatDate, parseDate }        // ✓ object literal, plain keys
module.exports.formatDate = ...                   // ✓
Object.defineProperty(exports, 'x', { ... })      // ✓
module.exports = require('./other')               // ✓ simple reexport — it follows it
```

Because it is a **heuristic over source text, not an evaluation**, export shapes it cannot
read produce no named exports at all:

```js
module.exports = makeExports()                    // ✗ it will not run makeExports()

for (const name of ['formatDate', 'parseDate']) { // ✗ computed keys
  exports[name] = impls[name]
}

const api = {}                                    // ✗ not an object literal at the
api.formatDate = formatDate                       //   assignment site
module.exports = api

module.exports = Object.assign(mainFn, {          // ✗ common "callable with properties"
  formatDate,                                     //   package shape
})
```

Consuming any of those with a named import fails at **link time**, before your app runs a
line — note it is a `SyntaxError`, not a `TypeError`:

```
SyntaxError: Named export 'formatDate' not found. The requested module
'@acme/utils' is a CommonJS module, which may not support all module.exports
as named exports.
CommonJS modules can always be imported via the default export, for example
using: import pkg from '@acme/utils'; const { formatDate } = pkg;
```

That final sentence states the one guaranteed contract:

> **The default import of a CJS module is always `module.exports` itself.**
> No heuristics, no static analysis, no failure mode.

So *"you can't use named imports from CJS"* is wrong in the common case and right in the
general case — and the deciding factor is the lexer's reading of the export shape, never a
compiler flag.

### Why this is a realistic monorepo failure

Nobody edits a dependency's source to break it. Someone changes its **build** — swaps `tsc`
for a bundler, turns on minification, wraps the export in `Object.assign` to make the
package callable — and the emitted shape stops being lexer-legible. The consuming app's
source never changed. Connects forward to **4.2 (bundling libraries)**.

**Diagnostic tell:** app dies before printing anything, with a `SyntaxError` naming a module
you didn't write → CJS/ESM interop failure, not a bug in your code.

### Names vs values — the quiet failure mode

The lexer decides which **names** exist. The runtime `module.exports` object decides what
those names are **worth**. When the two disagree, interop stops failing loudly and starts
failing silently:

```js
// @acme/ghost
exports.real = 1
exports.ghost = 2
delete exports.ghost      // lexer already recorded 'ghost' from the source text
```

```js
import { real, ghost } from '@acme/ghost'
// real  -> 1
// ghost -> undefined      no error, no warning
```

Verified output:

```
real          : 1
ghost         : undefined   <- lexer said it exists
namespace keys: [ 'default', 'ghost', 'module.exports', 'real' ]
```

Realistic triggers: conditional exports (`if (isNode) exports.fs = ...`), platform-gated
builds, packages that prune their own exports at load time.

## Where `esModuleInterop` actually belongs

A real thing, one layer up. When TypeScript compiles ESM-looking source **down to
CommonJS**, `import x from 'pkg'` must become something. Without `esModuleInterop`, TS emits
approximately `const x = require('pkg')` and requires an `__esModule` marker to permit a
default import at all. With it, TS emits a helper:

```js
// what __importDefault does, conceptually
const _pkg = require('pkg')
const pkg = _pkg && _pkg.__esModule ? _pkg : { default: _pkg }
```

It wraps a plain CJS export in `{ default: ... }` so default-import syntax behaves the way
Node's real ESM would.

Keep the two layers distinct:

| Layer | Component | Acts at |
|---|---|---|
| TypeScript | `esModuleInterop`, `__importDefault`, `__esModule` | compile / emit time |
| Node | `cjs-module-lexer`, default-import contract | runtime linking |

Revisited in **3.2 (module resolution modes)**.

## The reverse direction: `require()` of ESM

Historically threw `ERR_REQUIRE_ESM`. As of **Node 22.12 / 23+**, `require()` of an ESM
graph works, provided the graph contains no top-level `await` — one that does throws
`ERR_REQUIRE_ASYNC_MODULE`. This meaningfully softens dual-publishing pain; used again in
**4.3**.

*(Note: the reason top-level await is the blocker depends on ESM's asynchronous evaluation

## Check-in question — **ANSWERED**

A teammate ships this package:

```js
// @acme/logger — package.json has "type": "commonjs"
const createLogger = (opts) => { /* ... */ }
module.exports = createLogger
module.exports.createLogger = createLogger
module.exports.LEVELS = ['debug', 'info', 'error']
```

The ESM app writes:

```js
import createLogger, { LEVELS } from '@acme/logger'
```

### Part 1 — does it work?

**Student's answer:** *"I don't think it works because of `module.exports = createLogger`."*

**Verdict: it works.** Right line flagged, wrong conclusion drawn from it.

`module.exports = createLogger` assigns a **bare identifier**, not an object literal, so the
lexer extracts no names *from that line*. But it does not **cancel** anything — the lexer
scans the whole source and collects every detectable pattern. The two following lines are
textbook member assignments:

```js
module.exports.createLogger = createLogger   // ✓ detectable
module.exports.LEVELS = [...]                // ✓ detectable
```

so both become named exports. The default import never involved the lexer at all.

Verified output:

```
default import is a function : function
named import LEVELS          : [ 'debug', 'info', 'error' ]
default === module.exports?  : true
```

**Where the instinct was right:** delete the two member assignments and
`module.exports = createLogger` becomes the only export statement — the lexer finds nothing
and `import { LEVELS }` fails at link time. That is the `Object.assign(mainFn, {...})`
failure. The dangerous pattern was identified correctly; it was over-applied to a file that
*also* contained legible assignments.

**The takeaway that generalises:** `module.exports = fn` + `module.exports.helper = ...`
works, while `module.exports = Object.assign(fn, { helper })` does not — **identical runtime
behaviour, different source shape**. A refactor a reviewer would call cosmetic can break
every consumer.

### Part 2 — what does `import * as logger` give you?

**Student's answer:** *"the whole exports module with everything in it."*

Everything is indeed present — but the namespace **is not `module.exports`**. It is a fresh,
sealed **Module Namespace Object** fabricated by Node: lexer-found names plus a synthesized
`default` pointing at `module.exports`.

```
CJS namespace keys     : [ 'LEVELS', 'createLogger', 'default', 'module.exports' ]
typeof ns              : object
ns callable?           : false        <- module.exports IS a function...
ns.default callable?   : true         <- ...but the namespace is not it
ns[Symbol.toStringTag] : Module
ns is extensible?      : false

True ESM namespace keys: [ 'LEVELS', 'createLogger' ]
ESM ns has "default"?  : false
```

Three consequences:

1. **`ns(opts)` throws** `TypeError: ns is not a function`, though the package's export is a
   perfectly good function. Real migration bug: CJS `const logger = require(...); logger(o)`
   rewritten as `import * as logger` dies.
2. **A CJS namespace always has `default`; a true ESM namespace has `default` only if the
   module declares one.** That is the asked-for difference.
3. **The namespace is non-extensible** — monkey-patching a `require()` result is a common CJS
   trick that simply cannot work in ESM.

### Bonus discovered in-session — the `'module.exports'` key

ES2022 permits arbitrary string names in module namespaces, and Node uses that to expose the
raw `module.exports` under the literal name `"module.exports"`. It is the clean escape hatch
for the non-callable-namespace trap:

```js
import { "module.exports" as logger } from '@acme/logger'
logger(opts)          // ✓ this IS module.exports, not a namespace wrapper
```

Verified: `typeof logger === 'function'`, and `logger.LEVELS` resolves.

### Reproducing it

Verified on **Node v24.18.0**.

```
logger-demo/
  package.json                                  { "type": "module" }
  node_modules/@acme/logger/package.json        { "type": "commonjs", "main": "./index.js" }
  node_modules/@acme/logger/index.js            the CJS source above
  node_modules/@acme/esm-logger/package.json    { "type": "module",   "main": "./index.js" }
```

## Key takeaways (interop third)

1. CJS exports are a runtime value; ESM bindings must be resolved before evaluation. That
   mismatch is the entire problem.
2. Node bridges it with `cjs-module-lexer` — a static source scan, not an execution. Named
   imports from CJS work only when the export shape is statically legible.
3. `import pkg from 'cjs-package'` is the always-safe form: default import **is**
   `module.exports`.
4. `esModuleInterop` is TypeScript emit. It has no say in Node's runtime linking.
5. Interop failures surface as link-time `SyntaxError`s, and are typically triggered by a
   *build* change in a dependency, not a source change in the app.
6. The lexer supplies the **names**; the runtime `module.exports` supplies the **values**.
   Disagreement between them yields a silent `undefined` — the quiet failure mode.
7. `import * as ns` on a CJS module gives a **synthesized, sealed namespace**, not
   `module.exports`: never callable, always has `default`, never extensible. Use
   `import { "module.exports" as x }` when you need the raw value.
8. Every ergonomic property of CJS was bought by giving up a static one. That trade is the
   root cause of almost everything awkward in Modules 1–4.
9. ESM imports are **live, read-only references**, not value copies — the one difference that
   yields plausible wrong values instead of an error.
10. Import declarations are **hoisted**: the whole dependency subgraph evaluates before the
    importer's first line. Dynamic `import()` is the only conditional form.
11. Top-level await makes evaluation asynchronous, which is why `require()` — synchronous by
    a 2009 decision — can never load such a module.

## The three failure modes of lesson 1.1, by loudness

Worth holding as one picture, because diagnosability is the practical skill here:

| Failure | When | Symptom | Demo |
|---|---|---|---|
| Lexer finds no names | link time | `SyntaxError`, names the package, nothing executes | `1.1-cjs-named-exports-lexer` |
| Namespace is not `module.exports` | call site | `TypeError: ns is not a function` | `1.1-cjs-namespace-object` |
| Lexer name without runtime value | never fails | silent `undefined`, dies later elsewhere | `1.1-lexer-names-vs-runtime-values` |
| Live binding vs value copy | never fails | *plausible wrong values* | (semantics section) |

Descending diagnosability. The last two are the ones that cost days.
