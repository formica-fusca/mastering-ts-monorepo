## Placement context

Third lesson of Module 1, delivered the same day as 1.2 (whose exercises are still open).

1.2 ended with `LOAD_AS_DIRECTORY` reading a single field, `main`, to pick a package's entry
file. This lesson is about the field that replaced that contract. Everything here is a
lookup table consulted by the two resolvers already covered; no new resolver is introduced.

**Goal stated at the start:** read any `package.json` and say exactly which specifiers
resolve, to which file, under which consumer, and which are refused even though the file
exists.

## Concept — from an entry point to a public interface

`main` answers one question: what does `require('pkg')` load? It says nothing about
`require('pkg/lib/util')`, which simply works if the file is there. The package has no
interior; every file is public API by accident, and every moved file is a breaking change
for somebody.

`exports` turns the package inside-out. It maps **public specifiers** to **private files**.
Anything absent from the map does not exist for consumers.

```json
{
  "name": "sealed",
  "main": "./legacy-main.js",
  "exports": {
    ".": "./dist/index.js"
  }
}
```

```
require('sealed')                        -> sealed/dist/index.js
import 'sealed'                          -> sealed/dist/index.js
require('sealed/internal/secret.js')     -> ERR_PACKAGE_PATH_NOT_EXPORTED
require('sealed/package.json')           -> ERR_PACKAGE_PATH_NOT_EXPORTED
require('sealed/dist/index.js')          -> ERR_PACKAGE_PATH_NOT_EXPORTED
```

Three things to read off that output:

1. `main` was ignored. When `exports` exists it wins, for both resolvers.
2. `internal/secret.js` exists and is refused.
3. The **real path of the entry itself** is refused. Consumers may use the public name `"."`
   only, never the physical location. That is what lets `dist/` be renamed tomorrow without a
   breaking change.

The error code matters: `ERR_PACKAGE_PATH_NOT_EXPORTED`, not `MODULE_NOT_FOUND`. The walk
succeeded, the package was found, and the package *declined*. The fix is almost never on the
consumer side.

## Mechanism — how the map is read

The resolver step is `PACKAGE_EXPORTS_RESOLVE`. After the 1.2 walk finds
`node_modules/<name>/package.json`, the specifier is split into package name and subpath,
where the bare name alone means `"."`. Then:

```
exports is a string          → shorthand for { ".": "<string>" }
exports is an object
  keys start with "."        → subpath map; look up the subpath (exact, then patterns)
  keys do not start with "." → conditions object for "." itself
target is a string           → resolved as an exact relative URL, no probing
target is an object          → conditions: walk keys IN ORDER, first match wins
target is an array           → fallbacks: first entry that resolves
```

Two of those lines carry nearly all the bugs.

### Targets are exact

```json
{ "name": "noprobe", "exports": { ".": "./index" } }
```

```
require('noprobe')   -> MODULE_NOT_FOUND
                        Cannot find module '<root>/node_modules/noprobe/index'
```

This is `require()`, the resolver that probed `.js` happily in 1.2. Inside an `exports`
target it does not. The map speaks the ESM dialect for both resolvers: full path, extension
included.

### Conditions are matched by key order

Node does not rank conditions. The object's key order *is* the precedence list.

```json
{
  "name": "badorder",
  "exports": {
    ".": {
      "default": "./fallback.cjs",
      "import": "./index.mjs"
    }
  }
}
```

```
import 'badorder'   -> badorder/fallback.cjs
```

`default` matches every consumer, so listed first it shadows everything after it. The ESM
entry is dead code; no warning, no error, just the wrong file everywhere. `default` goes
**last**, always.

## Conditional exports — one name, several files

The conditions object serves different consumers from one specifier. Node's built-in
conditions: `import`, `require`, `node`, `node-addons`, `default`. Tooling adds its own; the
ones that matter in a TypeScript monorepo:

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

`types` is matched by TypeScript, never by Node, which skips unknown conditions. It must be
**first**: TypeScript stops at the first match, and placed after `import` it would never be
reached. Bundlers add `browser`, `development`, `production`; Node honours custom conditions
through `--conditions=name`. The two fixed positions: `types` first, `default` last.

**Which pairs can collide.** Order only matters between conditions that can **both** match a
single request. `import` and `require` never collide: one request is one or the other.
`default` collides with everything. `node` collides with `import` and `require`. A custom
condition like `development`, when active, collides with both, and must sit above them to
win. Reasoning about collisions, rather than shuffling keys, is the skill.

### The dual package hazard, previewed

```json
{ "name": "dual", "exports": { ".": { "import": "./index.mjs", "require": "./index.cjs" } } }
```

```
require('dual')                   -> dual/index.cjs
import 'dual'                     -> dual/index.mjs
state shared between the two?     -> import sees 42, require sees 0
```

Same specifier, two resolved paths, and by 1.2's rule two module instances with separate
state. An app that imports `dual` while a dependency requires it has two copies in one
process. Lesson 4.3 is about designing packages so this cannot happen. The demo reproduces
it in one process via `createRequire`.

## Subpath patterns

A single `*` is allowed, matching any string including slashes:

```json
{
  "name": "patterns",
  "exports": {
    ".": "./src/index.js",
    "./utils/*": "./src/utils/*.js",
    "./package.json": "./package.json"
  }
}
```

```
require('patterns/utils/math')      -> patterns/src/utils/math.js
require('patterns/utils/math.js')   -> MODULE_NOT_FOUND
                                       Cannot find module '.../src/utils/math.js.js'
require('patterns/package.json')    -> patterns/package.json
```

The `*` is **textual substitution**, not a glob. `math.js` became `math.js.js`. And
`package.json` had to be exported explicitly: sealing seals the manifest too, and many tools
read a dependency's `package.json` for its version.

## The smaller fields

**`main`**: keep it, as the fallback for tooling that predates `exports`. Point it at the
CJS entry, or the only entry. Node never consults it when `exports` exists.

**`types`** (top level): the equivalent fallback for TypeScript under the old
`moduleResolution: node`, which does not read `exports`. The `types` *condition* is what
modern resolution uses. Ship both until 3.2 settles your consumers' resolution mode.

**`module`**: not a Node field. Bundlers invented it to find an ESM build before `exports`.
Node ignores it. Seen alone, it marks a package that works in Vite and may not in Node.

**`type`**: from 1.1. Sets what `.js` means inside *this* package only.

**`files`**: whitelist of what is packed on publish or `pnpm pack`/`pnpm deploy`. Decides
what exists on disk at the consumer; `exports` can only point at what exists. Invisible in a
workspace (consumers are symlinked to the source tree), it bites in Docker builds (8.3) when
`dist/` is not listed.

**`imports`**: the private mirror of `exports`. `#name` specifiers usable only inside the
package, same conditions syntax. Node-native aliases without a compiler (compare `paths`,
lesson 3.3).

## TypeScript reads the same map

Discovered while building the demo: under `moduleResolution: nodenext`, TypeScript enforces
`exports` at compile time. A literal import of a non-exported subpath fails before Node ever
runs:

```
error TS2307: Cannot find module '@demo/config/lib/index.js' or its corresponding type declarations.
```

The demo's sealed-path probes are therefore built from strings. Two consequences for later:
`exports` mistakes surface in `tsc`, which is good, and TypeScript resolving a *different*
condition than Node (the `types` ordering bug) surfaces as types for the wrong file, which is
quiet and belongs to 4.4 (arethetypeswrong).

## Check-in question — **ANSWERED**

A workspace package ships this:

```json
{
  "name": "@demo/config",
  "type": "module",
  "main": "./dist/index.cjs",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

An ESM app in the same workspace does two things:

```js
import { load } from '@demo/config'
import pkg from '@demo/config/package.json' with { type: 'json' }
console.log(pkg.version)
```

Does this run? If not, which line fails, with which error code, and what is the one-line
change to the package that fixes it without weakening the encapsulation of anything else?

**Student's answer:** *"no it does not, because node resolves from the exports map, and
import is correctly defined. I guess the fix would be to swap, in the package, the import and
require lines."*

**Verdict: half right.** Actual run:

```
=== as shipped ===
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './package.json' is not
defined by "exports" in <root>/app/node_modules/@demo/config/package.json
imported from <root>/app/main.mjs
```

**Right:** it does not run, and because Node resolves through `exports`. The `"."` entry is
correct and line 1 would succeed on its own.

**Missed: which line.** Line 2 asks for subpath `./package.json`, which is not a key in the
map. Sealing seals the manifest. Also: line 1 never printed, although it would have worked,
because imports are hoisted (1.1) and the module fails to link as a whole. The failing line
is 2; the symptom is "nothing runs".

**Proposed fix, swapping `import` and `require`:** changes nothing, verified:

```
=== your fix: swap import and require ===
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './package.json' ...
```

Two separate reasons recorded, both worth having precisely:

1. The problem is in the **subpath map** (keys starting with `.`); the edit was in the
   **conditions object** of one subpath. Different level of the structure. Conditions choose
   *which file* for a subpath that exists; they can never create a subpath.
2. Order between `import` and `require` **never matters**, because a request is one or the
   other and can never match both. Order matters only between conditions that can collide
   (`default` vs anything, `node` vs `import`/`require`, custom conditions vs the built-ins,
   `types` vs whatever TypeScript would otherwise match).

**Actual fix**, one line in the subpath map:

```json
"exports": {
  ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js", "require": "./dist/index.cjs" },
  "./package.json": "./package.json"
}
```

```
line 1 ok: loaded via ESM entry (dist/index.js)
line 2 ok: 1.4.2
dist/index.js direct -> ERR_PACKAGE_PATH_NOT_EXPORTED     ← still sealed
```

**Diagnostic habit flagged for re-test:** name the *specifier* before reasoning about the
file. `'@demo/config'` and `'@demo/config/package.json'` are two subpaths looked up as two
keys before any condition is consulted. 1.2 trained this (name the importer, then the walk);
1.3 extends it (name the subpath, then the condition). Exercise 1.3-b targets the
collision-reasoning gap directly.

## Key takeaways

1. `main` names an entry point. `exports` defines a public interface, and everything outside
   it stops existing for consumers, including the entry's own physical path.
2. `ERR_PACKAGE_PATH_NOT_EXPORTED` means the walk succeeded and the package declined. Fix the
   package or stop reaching for an internal.
3. Two levels: subpath keys (start with `.`) name public names; condition keys choose a file
   for one name. Name the subpath before reasoning about conditions.
4. Targets are exact relative URLs for **both** resolvers: full path, extension, no probing,
   even under `require()`.
5. Conditions are matched in **key order**. `types` first, `default` last. Order only matters
   between conditions that can collide; `import`/`require` never do.
6. `*` in a pattern is textual substitution, not a glob. `./utils/*` → `./lib/utils/*.js`
   means `utils/math` works and `utils/math.js` becomes `math.js.js`.
7. Export `./package.json` explicitly. Everyone reads it.
8. `import` and `require` conditions pointing at two files create two module instances in one
   process: the dual package hazard (4.3).
9. `main` and top-level `types` stay as fallbacks for old resolution; `module` is a bundler
   convention Node ignores; `files` decides what exists on disk after packing; `imports` is
   the private `#alias` mirror.
10. TypeScript under `nodenext` enforces the same map at compile time (`TS2307`).

## Failure modes of lesson 1.3, by loudness

| Failure | When | Symptom | Where seen |
|---|---|---|---|
| Subpath not in map | link time | `ERR_PACKAGE_PATH_NOT_EXPORTED` naming the subpath | this file; demo break 2; exercise 1.3-a |
| Target without extension | link time | `MODULE_NOT_FOUND` on a path with no extension | "Targets are exact" |
| Pattern doubled an extension | link time | `Cannot find module '.../x.js.js'` | "Subpath patterns"; exercise 1.3-a |
| `default` listed first | never fails | wrong file for every consumer, types still pass | demo break 1; exercise 1.3-b |
| `types` not first | never fails in Node | TypeScript resolves types for the wrong file | 4.4 preview |
| Two conditions, two files | never fails | duplicated state across import/require consumers | demo "dual package hazard" |

The loud ones are fixed in minutes. The three quiet ones are where whole afternoons go.
