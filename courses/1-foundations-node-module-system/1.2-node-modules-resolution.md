## Placement context

Second lesson of Module 1, delivered after lesson 1.1 was **completed** (all three 1.1
exercises solved by the student in a scratch copy and reported passing; see the 1.1 file).

1.1 covered what Node does once it has a file: lex it, evaluate it, link it. This lesson is
the step before: turning the string in an `import` or `require()` into a file on disk.
Everything from Module 2 onward either exploits this algorithm (pnpm's layout, workspace
linking, hoisting) or re-implements it (TypeScript's `moduleResolution`, every bundler, Jest).

**Goal stated at the start:** given any specifier, any importing file, and any `node_modules`
layout, predict exactly which file Node loads, or exactly which error it raises.

---

## Concept — three kinds of specifier

A specifier is the string in the quotes. Node classifies it before doing anything else:

```
'./util'        relative     → resolved against the importing file's directory
'/abs/path.js'  absolute     → taken as-is
'greeter'       bare         → looked up in node_modules folders
'@demo/lib'     bare, scoped → same, two-segment name
'greeter/lib'   bare + path  → package lookup, then a subpath inside it
```

Relative and absolute are deliberately boring. Every interesting behaviour and every bug in
this lesson lives in the bare branch.

---

## Mechanism — the upward walk

For a bare specifier Node consults no registry, no config file, no global map. It walks
**up** the directory tree from the *importing file*, trying `node_modules/<name>` at each
level until the filesystem root. A file four levels deep asking which directories Node would
try:

```js
// apps/web/src/main.cjs
console.log(require.resolve.paths('greeter').join('\n'))
console.log(require.resolve('greeter'))
```

```
<root>/apps/web/src/node_modules
<root>/apps/web/node_modules
<root>/apps/node_modules
<root>/node_modules                     ← found here
/node_modules
/Users/Audrey/.node_modules             (legacy global folders; ignore)
/Users/Audrey/.node_libraries
/Users/Audrey/.nvm/versions/node/v24.18.0/lib/node

<root>/node_modules/greeter/lib/index.js
```

That list, read once, explains hoisting, phantom dependencies (1.4), and why a monorepo root
`node_modules` is both convenient and dangerous: any package above you on the path is
reachable whether or not you declared it.

Three properties of the walk that everything else depends on:

1. It starts from the **importing file's directory**, not from `cwd` and not from any
   "project root". Node has no concept of a project.
2. It goes **up only**. Never sideways into a sibling, never down into a child.
3. The **nearest** match wins. A "better" copy higher up is never considered.

### What happens at each candidate

Trimmed from the pseudo-code in the Node docs:

```
LOAD_AS_FILE(X)        try X, X.js, X.json, X.node
LOAD_AS_DIRECTORY(X)   read X/package.json → "main", then LOAD_AS_FILE(X/main)
                       fall back to X/index.js, X/index.json, X/index.node
```

So `require('greeter')` found `<root>/node_modules/greeter/`, read its `package.json`, saw
`"main": "lib/index.js"`, and loaded that. `main` is the only `package.json` field this
lesson needs; lesson 1.3 introduces `exports`, which takes precedence over it.

## Two resolvers, not one

Node ships two resolvers. They share the upward walk and disagree on almost everything else.
Same tree, two consumers:

```js
// apps/web/src/main.cjs
console.log(require.resolve('./util'))          // no extension
```

```js
// apps/web/src/main.mjs
try { await import('./util') } catch (e) { console.log(e.code, e.message) }
console.log((await import('./util.js')).default)
```

```
CJS:  <root>/apps/web/src/util.js                 ← probed .js for you

ESM:  ERR_MODULE_NOT_FOUND
      Cannot find module '<root>/apps/web/src/util' imported from .../main.mjs
      util loaded                                 ← only with './util.js'
```

The ESM resolver does **no extension probing and no `index.js` fallback** for relative
specifiers. The specifier is a URL and must name the file exactly. 1.1 presented this as
"mandatory extensions"; the origin is here, in the resolver, not in the syntax.

Why: every probe is a filesystem `stat`. CJS was designed for a server with a local disk,
where a dozen stats are free. ESM was designed to be the same algorithm in a browser, where
a probe is an HTTP round trip, so the spec forbade guessing. Node's ESM resolver kept that
discipline on local disk too.

| | `require()` (CJS) | `import` (ESM) |
|---|---|---|
| Relative, no extension | probes `.js`, `.json`, `.node` | error |
| Relative directory | tries `index.js` | error |
| Bare specifier | upward walk, `main`, then `index.js` | upward walk, `exports` if present, else `main` |
| Result type | absolute path | `file://` URL |
| Error code | `MODULE_NOT_FOUND` | `ERR_MODULE_NOT_FOUND` |

The error codes are diagnostic. `ERR_MODULE_NOT_FOUND` with an extensionless path in the
message means CJS-style imports in an ESM file. `Cannot find module 'x'` followed by a
`Require stack:` means the upward walk ran out of directories, and the stack tells you which
file started the walk.

## Symlinks, real paths, and module identity

The part of 1.2 that Module 2 is built on. Workspace tools (pnpm, npm, yarn) link workspace
packages into consumers' `node_modules` with symlinks. What does Node do with a symlink?

```
root/
  apps/web/node_modules/@demo/lib  →  ../../../../packages/lib   (symlink)
  packages/lib/
    index.js                       require('dep')
    node_modules/dep/              lib's own private dependency
```

```js
// packages/lib/index.js
const dep = require('dep')
module.exports = { whereIsDep: require.resolve('dep'), dep }
```

```js
// apps/web/src/symlink.cjs
const lib = require('@demo/lib')
console.log('resolved @demo/lib ->', require.resolve('@demo/lib'))
console.log('lib resolved dep   ->', lib.whereIsDep)
```

```
resolved @demo/lib -> <root>/packages/lib/index.js
lib resolved dep   -> <root>/packages/lib/node_modules/dep/index.js
```

Node followed the symlink and reports the **real path**. When `lib` then asked for `dep`,
the walk started from `packages/lib/`, the real location, not from
`apps/web/node_modules/@demo/lib/`. **A package resolves its dependencies from where it
actually lives.**

Node has a flag that disables this, which is the easiest way to see what the default buys:

```
$ node --preserve-symlinks apps/web/src/symlink.cjs
resolved @demo/lib -> <root>/apps/web/node_modules/@demo/lib/index.js
lib resolved dep   -> <root>/apps/web/node_modules/@demo/lib/node_modules/dep/index.js
```

### Identity is the resolved path

The module cache is keyed by resolved filename:

```js
console.log(Object.keys(require.cache).filter(k => k.includes('greeter')))
// [ '<root>/node_modules/greeter/lib/index.js' ]
```

One resolved path, one instance. Two resolved paths, two instances, even for identical bytes.
The demo makes this concrete with a dependency that holds a call counter, consumed by both
the app and a library:

```
default (realpath):   same dep instance for web and lib? true    calls: 1, then 2
--preserve-symlinks:  same dep instance for web and lib? false   calls: 1, then 1
```

Two instances of a stateful module is "two copies of React", a singleton that is not one,
`instanceof` failing across packages, an emitter nobody else is listening to. Node made
real-path resolution the default in 2016 to rule this out by construction. pnpm's layout
(one copy per package in a store, symlinked everywhere) is viable only because of it.

A side effect met while building the demo: in TypeScript, `import * as dep from 'dep'`
compiled to CJS emits `__importStar(require('dep'))`, a synthesized namespace wrapper, so
`dep === lib.dep` is `false` even with one instance. Same namespace-is-not-`module.exports`
trap as 1.1, produced by the compiler this time. The demo uses `import dep = require('dep')`
to compare `module.exports` itself.

## Who else implements this algorithm

Node, twice. TypeScript, which must find `.d.ts` files the way Node finds `.js`, with modes
named after Node behaviours (`node16`, `nodenext`, `bundler`; lesson 3.2). Every bundler
(esbuild, Rollup/Vite, webpack), each with its own copy and small deviations. Jest, with
another. A large share of "works in `tsc`, breaks at runtime" and "works in Vite, breaks in
Jest" bugs are two of these resolvers disagreeing on a case the spec leaves open. The
diagnostic move is always the same: ask each tool what it resolved, and compare.

## Asking Node what it resolved

```bash
node -p "require.resolve('pkg')"           # CJS answer, from cwd
node -p "require.resolve.paths('pkg')"     # the candidate directory list
node --input-type=module -e "console.log(import.meta.resolve('pkg'))"   # ESM answer
NODE_DEBUG=module node app.js              # trace every CJS resolution
```

From a specific file's point of view, `createRequire(pathToThatFile).resolve('pkg')`.

## Check-in question — **ANSWERED**

Take the symlink tree above and make one change: delete `packages/lib/node_modules/dep`
entirely, and instead install `dep` only at `apps/web/node_modules/dep`. The app's
`package.json` declares `dep`; `@demo/lib`'s does not, but its author "knows it's there".

Run `node apps/web/src/symlink.cjs` with default settings. What happens, and why? Then: does
the answer change with `--preserve-symlinks`?

**Student's answer:** *"dep install would move to the root node_modules, and preserve
symlinks would give the same result."*

**Verdict: wrong on both halves.** Actual run:

```
=== default (realpath) ===
Error: Cannot find module 'dep'
Require stack:
- <root>/packages/lib/index.js
- <root>/apps/web/src/symlink.cjs

=== --preserve-symlinks ===
resolved @demo/lib -> <root>/apps/web/node_modules/@demo/lib/index.js
lib resolved dep   -> <root>/apps/web/node_modules/dep/index.js
```

**First half, "it would move to root".** Nothing moves. The question handed over a layout
and asked what *Node* does with it; the answer described what a *package manager* would do
at install time. Hoisting is an install-time decision by pnpm or npm. Resolution is what Node
does at require time with whatever it finds. Two layers.

This is the same pattern as the 1.1 diagnostic answer, where a TypeScript emit option
(`esModuleInterop`) was used to explain Node runtime linking. **Recurring misconception to
re-test:** answering a question about one layer with the behaviour of an adjacent layer
(package manager / compiler / runtime). Natural re-test points: 1.4 (hoisting vs resolution),
2.2 (pnpm layout vs Node walk), 3.2 (TypeScript resolution vs Node resolution).

**Second half, "same result".** Opposite results. The two walks by hand:

```
default:  lib's real path is packages/lib/index.js, so
          packages/lib/node_modules      ✗
          packages/node_modules          ✗
          root/node_modules              ✗   (dep is not here)
          /node_modules                  ✗   → MODULE_NOT_FOUND

preserve: lib's path is apps/web/node_modules/@demo/lib/index.js, so
          apps/web/node_modules/@demo/lib/node_modules   ✗
          apps/web/node_modules/@demo/node_modules       ✗
          apps/web/node_modules                          ✓  dep found
```

The default is the **correct** behaviour and the error is a gift: `@demo/lib` uses `dep`
without declaring it, real-path resolution refuses to let it borrow the app's copy, and the
require stack names the library at fault. With `--preserve-symlinks` the undeclared
dependency silently works until a second consumer does not happen to install `dep`. That is
a phantom dependency, lesson 1.4, seen here at the mechanism level.

**Reading habit to keep:** read a require stack bottom-up. The real path of the failing
importer tells you *whose* dependency is missing, which in a workspace is the difference
between "the app forgot" and "a workspace package forgot".

## Key takeaways

1. Three specifier kinds: relative, absolute, bare. Only bare specifiers consult
   `node_modules`.
2. The walk starts at the **importing file's real directory**, goes **up only**, and the
   **nearest** `node_modules/<name>` wins. Node has no notion of a project root.
3. At each candidate: `LOAD_AS_FILE` probes extensions, `LOAD_AS_DIRECTORY` reads `main`
   then falls back to `index.js`. (CJS only.)
4. The ESM resolver refuses to guess: no extension probing, no directory index. Mandatory
   extensions are a resolver property, not a syntax rule.
5. `MODULE_NOT_FOUND` + `Require stack:` is the CJS walk running out of directories;
   `ERR_MODULE_NOT_FOUND` with an extensionless path is CJS habits in an ESM file.
6. Symlinks are resolved to **real paths** before the walk. A package finds its
   dependencies from where it really lives, not from where it was linked.
7. Module identity is the resolved path. One path, one instance; two paths, two instances
   with separate state. `--preserve-symlinks` exists mainly to show you why the default is
   right.
8. Node, TypeScript, every bundler and Jest each implement their own resolver. When tools
   disagree, ask each what it resolved.
9. Keep layers apart: the package manager decides the layout at install time; Node resolves
   against the layout at require time. Answer the question at the layer it was asked.

## Failure modes of lesson 1.2, by loudness

| Failure | When | Symptom | Where seen |
|---|---|---|---|
| Walk runs out of directories | require time | `Cannot find module 'x'` + require stack | demo break-it; exercise 1.2-b |
| CJS habit in ESM file | import time | `ERR_MODULE_NOT_FOUND` on an extensionless path | this file; exercise 1.2-a case 4 |
| Nearer copy shadows the intended one | never fails | wrong version loaded, plausible behaviour | exercise 1.2-a cases 1, 2, 6 |
| Two resolved paths for one package | never fails | duplicated state, `instanceof` false, "two Reacts" | demo `--preserve-symlinks` mode |

As in 1.1: the loud ones cost minutes, the quiet ones cost days.
